# moon_shadow_example

A module that reads **its own** `moon.mod`, git state and build variant at
runtime through `moon_shadow`.

```moonbit nocheck
let info = @moon_shadow.current()
println(info.name)    // "PaiGack/moon_shadow_example"
println(info.version) // "999.999.999"

let git = @moon_shadow.git()
println(git.branch)                  // "main"
println(git.to_version_string())     // "main <short-commit>", "-dirty" if tracked files changed

let build = @moon_shadow.build()
println(build.moon())                 // "moon 0.1.20261020"
println(build.profile)                // "debug" or "release"
println(build.target)                 // "wasm-gc", "js", "native"...
```

Run it from this directory:

```
moon run --target native cmd/main
```

The `gen` rule in `shadow/moon.pkg` runs the generator on `native`, so no
JavaScript runtime is involved; the example itself builds for `js`, `wasm-gc`
and `native` too.

## How the metadata gets in

Every value is baked in at build time: `moon_shadow` reads metadata through
the virtual package `PaiGack/moon_shadow/shadow`. This module implements it in
`shadow/` and points `overrides` at that package:

```moonbit nocheck
options(
  overrides: [ "PaiGack/moon_shadow_example/shadow" ],
)
```

`shadow/generated.mbt` is committed, so a clean clone needs no extra step.
It is regenerated by the `gen` rule in this module's `shadow/moon.pkg`, on
every `moon check`, from this module's `moon.mod` plus the git state of this
checkout — so editing `moon.mod` is enough, no separate generation step.
Git is not a rule input: a new commit does not invalidate the generated file,
so clean it (`rm shadow/generated.mbt` or `moon clean`) to pick one up.

The generator is the published package's `gen` package, run straight out of
`.mooncakes` where `moon add` stages it, so this module needs nothing but the
registry dependency.
